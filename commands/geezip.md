## 没有输入内容时 → 跑环境自检，报告状态

```bash
python "<GeeZip>/run.py" 自检
```

然后**用大白话**告诉用户现在能不能干活：

- **全部 OK** → 「环境正常，可以开工。告诉我你要哪块地、哪一年就行。」
- **缺 Python 包** → 自己跑 `pip install -r "<GeeZip>/requirements.txt"`，装完重跑自检
- **没找到 GeeLo** → 自己跑 `node "<GeeZip>/装GeeLo.js"`，它 clone + npm install，
  跑完重跑自检再报
- **缺项目 ID / 凭据** → 跑 `node "<GeeLo>/测试台/认证.js"`，它自动开浏览器；
  告诉用户「点一下『允许』就行」。**不要让他把凭据内容贴给你。**
- **连接失败且报 TIMEOUT** → 先让用户确认代理软件在跑，这是最常见的根因

别把自检的原始输出整段糊给用户，挑出他要做的事说。

## 有输入内容时 → 先判断该不该用 GeeZip

**这一步不能跳。** 不是所有下载都值得上 GeeZip：

- 只是写/调一个普通 GEE 脚本 → **改用 geelo skill**
- 要跑神经网络、要逐像元不确定性 σ → **改用 geedl skill**
- **数据太大下不动、下载太慢、撞配额或 EECU** → 这就是 GeeZip 的场合，开工
- **要下几十个波段、几十个时相** → 特别适合，波段越多越划算
- 就下一景、几个波段、小范围 → **直接下更快**，如实告诉用户别折腾
- 要逐位精确的存档 → **别用**，它是有损的

判断完**先把结论说一句**（"这个量直接下就行，用不着 GeeZip"
或 "24 个波段确实该压一下"），再动手。

## 确定要用 → 按这个顺序

```bash
python run.py 自检 → 取数 → 训练 → 导权重 → 门禁 → 下载 → 解码 → 汇总
```

或者一条 `python run.py 全部`。

**先小后大**：第一轮用 `--npix 8000 --轮数 60` 和一小块 ROI 把链路跑通，
确认没问题再放大。这能省用户不少配额。

不确定压多狠合适，先扫一遍：

```bash
python run.py 训练 --k扫 2 3 4 6
```

它会打一张表：每个 k 对应的下载量和还原误差。挑一个用户能接受的，
写进 `配置.txt` 的 `k` 或者后续步骤带 `--k`。

三条重点：

1. **两道核对都过了才许下载。** 结论是脚本自己判的（`GATE_RESULT PASS/FAIL`），
   没过 `下载` 会直接拒绝执行。**不要想办法绕过。**
2. **跑通不等于对。** 跑完再看一层数值 —— 量级对吗、讲得通吗。
3. **报告要诚实。** 压缩比按实际传输字节算、基线用 uint16 不是 float32；
   还原误差要和传感器自身定标精度比。

## 交付时说什么

用户关心的就三件事，按这个顺序说：

1. **少下了多少** —— 从 X MB 降到 Y MB，几倍
2. **差了多少** —— 还原误差 Z，和传感器自身噪声（Landsat ≈ 0.005）比是什么概念
3. **图** —— `产物/图/` 下的三联图（原图 / 隐层 / 还原）

用户可能会问「换块地还能用吗」。跑一下用数据回答，别猜：

```bash
python run.py 外推 --roi <另一块地的 W S E N>
```

单期影像换地方基本不掉；季相那套跨气候区会明显退化。**退化了照实说。**

成果写到**当前工作目录**的 `产物/`（需要独立管线就
`python run.py 新建 "<目录>"`），探针和临时脚本写临时目录。

交付时附上实跑输出当证据。跑不通就说跑不通。
